# Standalone Building Generator

## Purpose and locations

The sibling `../BuildingGenerator` project is a standalone Windows authoring tool. It takes a building description, numeric width/depth from 1–20 tiles each, and all nine `BuildingSideRequirement` options for North/East/South/West. Condition defaults to **Vandalized**, and materials default to **City colors**. It uses either the official Codex CLI with the user's ChatGPT login or the official Claude Code CLI with the user's Claude login (chosen under Connection settings → AI provider) to design structures. Both run headless with the same JSON schemas, no tools, and a temporary working folder; the standalone README's "Claude Code provider" section lists the exact flags. A **Reasoning effort** setting (CLI default / Low / Medium / High) controls thinking, which is most of the request time: one house took 190 s with Claude's defaults (Opus) and 69 s with model `sonnet` at Medium. Geometry, checks, preview, and export run locally. Start it through `../BuildingGenerator/Run.cmd` or `../BuildingGenerator/dist/BuildingGenerator.exe`.

The Unity integration lives in `Assets/Editor/BuildingGenerator/GeneratedBuildingImporter.cs`. It is editor-only. It adds no runtime generator or networking dependency. The standalone README documents build commands and the detailed schema/workflow.

The AI CLI process stdin (Codex or Claude Code) is explicitly UTF-8 without a byte-order mark, independent of the Windows console encoding. Output/error streams are also decoded as UTF-8. This is required even for English descriptions because architectural instructions include Unicode symbols. The regression check `dotnet run --project Tests/Tests.csproj -- --encoding` sends a full multilingual prompt through the real process runner to a strict UTF-8 child under Latin-1 console defaults; the original code fails and the fixed code preserves the prompt exactly.

## Description and category rules

The description controls building type, room layout, floors, materials, and requested decoration. With no extra detail requested, Complex buildings have minimally playable empty interiors. There is no fixed-template selection step; the AI writes a constrained architectural plan.

Explicitly requesting a **Simple** structure means a `SimpleBlocking` building: no accessible interior and a solid footprint extending to all lot edges. The app's type selector can force this category. The geometry compiler enforces a full-lot solid box regardless of AI-provided interior elements. Blockers support height and color, without detailed facades.

## Fixed geometry and material rules

`Core/Rules.cs` defines the 20-tile input limit, six-unit roof minimum, and canonical side names. `Core/Geometry.cs` enforces the following independently of AI compliance:

- Every lot gets an asphalt base at exactly Y=0, matching the handmade `BuildingPlane`, with a 0.1-unit base thickness. Visible top faces are clipped beneath ground-floor slabs (respecting their holes), so asphalt and floors meet without coplanar flicker. Simple blockers cover their entire base, so its top faces are omitted. Floor and asphalt colliders together support the lot. Asphalt colour approximates `Assets/Materials/SourceGround.mat` (#A4A4A4).
- Simple blockers are at least six units high. Every roof/eaves level of a Complex lot's **Main** structure below Y=6 gets a sealed solid extension to Y=6, retaining the original ceiling underside and courtyard cutouts. **Secondary** structures (garages, sheds, annexes, outbuildings) are padded to five units instead, so a one-storey garage stays lower than a two-storey house. Padding is one solid block in the structure's own wall colour, without storey bands. Both minimums exist so players cannot parkour out of the map. Padding adds no playable floor; the description still determines floor count. Open parks/courtyards have no roof and no artificial height requirement.
- Roofs are fitted to their own structure's walls (`Geometry.FitRoofs`): a roof slab ending at a wall centreline, or up to 0.3 short of it, is widened to the wall's outer face, so no roof or filler ledge exists for players to walk along. Edges at other structures and authored overhangs are kept; the saved plan is unchanged.
- Where a storey band meets a neighbouring structure at a facade corner, the band recess corner is closed out to the facade in the band's material, so the band ends in band colour flush against the neighbour from any angle.
- Flat surfaces never overlap at nearly the same height. Asphalt is omitted under anything resting on the lot (floor/balcony slabs with underside at most 0.05 and top at most 0.3, their door thresholds, ground covers); covers are cut under such slabs; slabs overlapping within 0.05 render the overlap once (earlier slab wins); thresholds skip slabs already covering them. Validation reports any remaining overlapping flat surfaces within 0.05 (floors, balconies, ground covers, exposed lot) as flicker.
- Flat ground covers (lawns, paths, driveways, flat Structure paving) never overlap: each is cut where a higher (or later, equally high) cover lies on it, and asphalt is omitted beneath them. Overlapping covers only hundredths apart used to flicker in triangular wedges.
- The route checker samples walkable surfaces with a hairline tolerance, so doors lying exactly on a 0.4-unit sampling line are not falsely unreachable. Rerolling points rejects only errors the new points introduce; a building that already fails its checks still gets points, and its issues stay listed for a revision.
- Validation rejects stairs blocking a doorway (a step higher than a step-up within 1 unit in front of either side) or running across a window (steps within 0.5 of the wall above its sill). Walls poking up to 0.6 past a perpendicular wall into open air are trimmed at compile time: interior walls to its inner face, facade walls to its outer face.
- Structures meet without slits: a wall end stopping up to 0.3 short of a perpendicular wall's face is extended to meet it (`Geometry.JoinedEnds`). Validation probes the compiled walls wherever one structure's wall ends within 1 unit of another structure, at heights where the neighbour stands, and reports any remaining see-through gap for the repair pass.
- No window opens onto another structure of the lot (`Geometry.DropBlockedOpenings`): a window in a wall stretch where another declared structure stands directly outside (e.g. upstairs over an attached garage roof) is closed at compile time; floor-level doors connecting the structures stay.
- Validation rejects any wall running into a window or doorway (e.g. a partition ending inside a window). It runs with the route checks, so an affected saved plan still opens and can be revised.
- Furniture within a small colour distance of the floor it stands on renders with a derived `_shade_<id>` material 18% lighter/darker; landscaping and structural details are unchanged.
- Floors stop at the centreline of exterior walls of the same structure standing on at least half of an edge (`Geometry.ClipFloors`), however far the plan extended them. Every storey band is a 0.1-deep recess (filled only where another structure stands against the facade), and no floor face is flush with a wall face, which used to flicker. Exterior doors get a floor threshold through the full wall thickness; balconies are never clipped.
- Exterior ground-storey walls of a raised floor continue down to Y=0, so the floor slab edge is never visible outside; door openings keep their threshold.
- A pitched roof's bounding volume is for collision checks only and never carves walls, so a neighbouring gable cannot notch the main facade above its eaves.
- **Orange / grey** overrides material assignments by geometry role: walls #FF9200 (matching `SourceWall.mat`), floors/stairs/ramps #A4A4A4, props a contrasting #72787E. The authored palette is preserved in the plan. **City colors** uses the AI palette: coordinated urban colours, neutral surfaces and stronger accents, with variation between buildings. For each new building the program rolls a facade scheme (`Prompt.FacadeScheme`): 65% one main wall colour with accents, 25% two-tone by storey split at a floor line (a one-storey building puts the second colour on its secondary structures or one storefront facade instead), 10% a separate colour per structure/wing. Revisions and Orange/grey get no scheme, so editing never repaints a building. Both use opaque colours, like the existing reference materials; no bitmap textures are generated.

In Orange / grey, roof top faces use dark grey #6C6C6C, matching the handmade prefab's `SourceRoad` roof material and contrasting with the lighter lot. Indoor ceiling undersides retain light grey #A4A4A4; vertical roof sides are orange up to the final height. The original roof slab and any sealed height extension compile into one volume, eliminating the grey horizontal stripe at their former join. Simple blockers also have dark grey tops and orange sides. Preview, export and collision share these meshes; Hide roof hides all roof material groups. Re-export saved plans to update existing models.

### Roof assemblies and tiers

Slabs, walls and detail boxes accept nullable `isRoof`. Explicit true marks structural roof components (including lower tiers, parapets and risers); explicit false preserves ordinary structure, furniture and playable terraces. Slabs with role Roof are always roof components. New AI output supplies these flags. Legacy null/missing flags infer conservatively from roof/tier/ceiling/parapet/coping names near the top of ordinary walls (including roof bases embedded into their tops); furniture/debris names are excluded, and Balcony slabs are not inferred as roofs. Roof slabs may form thick solid tiers: minimum thickness is 0.02 and their underside must remain at or above Y=0. The ordinary floor/balcony thickness limit stays 0.1–0.5.

`Core/RoofAssembly.cs` classifies the complete assembly. Every component compiles with mesh role Roof, so **Hide Roof** removes all tiers and associated roof walls/details while retaining playable floors. For axis-aligned overlapping tiers, compilation extends an upper part's bottom to the nearest lower roof surface underneath each patch, retaining its original top and footprint. Rectangular cutouts are preserved; no fill is added where there is no supporting roof footprint or an explicitly playable floor/balcony intervenes. Rotated decorative roof boxes are hidden with the assembly but retain their authored geometry. This closes floating tier gaps without changing the layered silhouette or rewriting the saved plan. Roof joining produces the same meshes for preview, collision and Unity export.

The compiler closes small endpoint notches between perpendicular walls whose heights overlap. It extends short corner ends to the other wall's outside edge, while preserving the original world positions of door/window openings and clamping extensions to the lot boundary. Already-complete butt joints remain unchanged. This seals common centerline-ended corners; it does not bridge intentional door-width gaps. The saved architectural plan is not modified.

**Normal** asks for orderly, intact furnishings. **Vandalized** asks for the aftermath of a zombie outbreak: multiple angled furniture assemblies, recognizable toppled shelving, scattered broken parts and looted stock. Larger interiors should contain several contextual incidents, such as improvised hospital triage, an abandoned refuge or a breached storage-room barricade. Barricade breaches must be at least 1.6 units wide; main routes need at least 1.4 units clearance. Explicitly empty/no-prop requests still take precedence. This is a generation instruction, not a random damage filter on an existing mesh. Changing either selector requires Generate or Apply revision before exporting; an existing tidy plan needs an AI revision to add damage.

Details now accept `group` (furniture assembly ID) and `yaw` (Unity +Y rotation in degrees, −180..180). Each group's parts use the same yaw and floor level. Coordinates describe the unrotated assembly; its pivot is the center of its combined XZ bounds. Blank groups rotate each box about its own center. Toppled furniture is modeled with its component boxes lying on their sides, then rotated as an assembly. Structural walls/stairs are left aligned. Old plans default to blank groups/yaw=0.

The compiler rotates actual detail vertices; preview, export and Unity colliders use identical triangles. The walking checker uses oriented footprints with clearance padding, spatial bins use their rotated bounds, and lot-bound validation checks the rotated extents. This preserves usable space around diagonal props instead of treating their entire bounding rectangle as solid. Rotation changes need no importer/schema-envelope version change: exports still contain baked vertices and indices.

## Adjacency and entrances

All nine options are sent to AI and exported unchanged into `BuildingDefinition`:

| Requirement | Design meaning |
| --- | --- |
| Any | No restriction or preference. |
| Requires Road | Main entrance on every required side, including park gates. |
| Requires No Road | Service/back-alley doors allowed; no main entrance. |
| Requires Ledge Down | Lot is above the cliff; a courtyard/outlook can face it. No entry from below. |
| Requires Ledge Up | Cliff rises beside the lot; treat as a blocked/back-alley side. |
| Requires Complex Building | Neighbor is enterable and often leaves perimeter space. |
| Requires No Complex Building | Excludes Complex only; does not imply a road or blocker. |
| Requires Blocking Building | Neighbor fills its entire lot; any usable alley must fit inside our own lot. |
| Requires No Blocking Building | Excludes blockers only; does not imply a road or Complex neighbor. |

New AI plans declare exterior entrance centers with a cardinal side and Main/Service intent. Validation requires a Main entry on each Road side, rejects main entrances on No Road/cliff/blocker sides, and checks that declared entries are clear/reachable. It does not seed walking routes through cliff/full-blocker boundaries. Service doors facing those boundaries can still be reached through the building's own alley from another side. The preview shows indicative neighboring strips/raised blockers; they are not exported. Existing world placement continues to handle neighbor restrictions and alley closures.

The first playable storey is `level=0`, not necessarily `y=0`: raised floors are supported when exterior stairs/ramps or a valid step connect them to the lot. Entrance markers include nullable `y`, the actual feet/threshold height. New plans specify it explicitly. For old plans missing this field, validation infers the first-storey doorway sill from nearby wall openings (using the profile's required headroom), then falls back to nearby first-storey slabs. All entrance clearance/reachability checks use that height. Lot asphalt remains exactly Y=0. Revisions/automatic repairs must preserve existing raised floors instead of lowering them to satisfy a zero-height assumption.

## Weapon, health and patrol points

The **Loot and patrol points** panel has separate 0–3× density sliders, Reroll buttons and Clear buttons for Weapon, Health and Patrol. Sliders set the next reroll's target; existing points remain until that group's button is used. Clear and 0× remove a group locally without an AI request. Other groups and architectural geometry remain untouched. The preview shows gold weapon, pink health and cyan patrol markers; Show points and the existing floor cutaway controls affect visibility only.

Calibration comes from the author's `BuildingGenerator/GeneratedBuildings/Ashford Police Station.buildingplan` and `Assets/Prefabs/WorldGeneration/Buildings/ComplexBuildings/3x2/Ashford Police Station.prefab`: **3 weapons, 2 health, 13 patrol** over **1923.92 square units of authored floor/balcony slab area after holes**. At 1×, Ashford requests those counts; 3× requests 9/6/39. Other buildings scale counts by the square root of their floor-area ratio so a large open room does not become a grid of markers. Each nonzero category has a minimum target of one; safety caps are 100 weapons, 100 health and 400 patrol. These are targets, not guarantees when space is limited.

New building generation automatically requests points after geometry passes validation. Old saved plans open with empty point lists; use the per-group reroll controls to populate them. Architecture revisions retain existing points where they remain reachable, snapping at most 0.4 units and discarding blocked/overlapping points rather than leaving stale targets inside changed walls. They do not trigger automatic marker AI rerolls.

Point generation uses the same AI provider connection/model, with `points.schema.json`, and returns only marker data. AI favors useful windows, corridor junctions, cover/hiding positions, selected rooms and meaningful loot POIs, rather than every room or a uniform grid. Floor positions match the handmade reference; pickups are beside furniture, not placed on top of tables. Patrol yaw can face windows/approaches. `Core/PointPlacement.cs` then snaps proposals onto reachable clear walking samples at the intended height, excluding roofs, stair treads, floor cutouts and solid furniture. Same-floor patrol spacing is at least 1.5 units, other marker pairs at least 0.85. One extra AI attempt requests any missing points; only safe placements are retained, and the UI reports placed/target counts.

Plan files store `points` and `pointSettings` separately from `plan`, so architectural AI edits cannot rewrite them. A canceled/failed reroll preserves its previous group. Targets are recomputed from the current building, and per-floor positions/levels are saved. New exports use envelope **version 2** with a point list; the importer (ScriptedImporter version 3) accepts both versions 1 and 2.

Unity imports empty child objects under **Generated Points** with the existing `PickupSpawnPoint` category Weapon/Health or `PatrolWaypoint` component, local position/yaw, and the default patrol gizmo radius. This matches the reference marker prefabs' components. It does not instantiate actual pickups or networked objects: existing host loot settings and `WorldLootSpawner` still choose how many markers to fill and which pickup prefabs to spawn. Existing patrol AI still chooses waypoints using its current behavior; the generator improves authored positions, not patrol ordering/brain logic.

The reference prefab and its handmade markers are never rewritten. If replacing an imported base underneath an existing manually marked prefab variant, remove the old manual markers or use a fresh generated prefab to avoid two sets. Generated marker child overrides should be treated as replaceable when rerolling/reimporting; the prefab root keeps its stable import identity.

## Generation and validation

**Generate building** starts a new plan from the description and controls. **Apply revision** edits the current plan using `revision.schema.json`: add/replace/remove operations targeting individual slabs, walls, furniture boxes, stairs, ramps, entrances or materials. Scalar edits are limited to name, category and Simple-blocker properties. Collection indices refer to the input snapshot; removals are applied after replacements, highest index first, and additions append. Duplicate/invalid targets are rejected. Edits apply atomically to a copy; untouched elements remain identical.

Revision prompts include the current plan, current controls, an explicit list of control changes, and the latest revision instruction. They omit the original generation description so obsolete prop counts/layout instructions do not restore removed elements. Unchanged condition/style selections do not ask AI to reapply them. Description edits are used for a new Generate request; put changes to the existing building in the revision box. The summary is updated to describe the result. The preview/export meshes are still rebuilt locally from the edited plan.

Automatic validation repair also uses targeted edits. Once the updated plan is displayed, the revision text clears even if navigation checks still fail, preventing accidental replay of an already-applied command. Cancellation, connection errors and rejected edit batches retain the previous displayed plan and revision text. Export remains disabled for invalid designs. This protects untouched plan elements; AI can still choose an incorrect edit target or change more within a replaced element than intended, so inspect the result.

The AI returns JSON matching `plan.schema.json`: palette, rectangular slabs/cutouts, walls/openings, stairs, ramps, and optional box details. The app never executes generated code. It compiles those elements to meshes grouped by floor, role, and material. The preview uses those same triangles. Normals face outward; UVs use world-scale coordinates.

The generation request includes `game-profile.json`, initially measured from this project:

- Tile size: 15 units.
- Player controller: radius .35, height 1.8.
- Humanoid NavMesh: radius .35, height 2.25, slope 45 degrees.
- Conservative step limit: .5, matching the controller rather than the NavMesh's .6.
- Authoring margins: doors at least 1.2 wide / 2.5 high, stairs at least 1.4 wide; stair slope capped at 40 degrees, risers at most .18, treads at least .27.

Validation checks geometry limits, palette references, lot bounds, door clearances, and stairs/ramps. A conservative 0.4-unit grid checks headroom and walking connectivity from available lot boundaries to floor/balcony areas. Spatial bins limit obstacle checks to nearby solids, and each slab checks only its own footprint, keeping large lots practical. Invalid designs get one automatic AI repair attempt. Remaining errors are shown in the app; export stays disabled. Plans can still be saved for later correction. Changed inputs disable stale export until the design is regenerated/revised.

These checks do not reproduce Unity's exact NavMesh, Fusion KCC, neighboring building placement, or zombie climbing. Final in-game movement checks remain necessary. Inspect overhangs according to the authoring contract in `ZombieAI.md`.

### Thin landscape surfaces (0.6.1)

Landscape detail boxes, including lawns and paving, may be as thin as 0.001 units. Their bottoms may extend down to Y=-0.1 (the lot-base depth), with tops between Y=0.001 and 60; fully buried, zero-thickness and non-finite boxes are rejected. Generation guidance recommends Y=0 and height=0.02 to keep grass above the asphalt. Ordinary furniture/structure height rules are unchanged. Legacy uncategorized lawn names are recognized as landscaping and protected during furniture rerolls; explicit categories take precedence. The existing mesh/export/import format already supports these boxes.

### Joined walls, roof choice and facade bands (0.7.0)

The Roof control offers **Suited to building** (default) and **Flat**. Suited generation normally uses gable/hip roofs for suburban homes and flat roofs where appropriate, such as apartment blocks and commercial/service buildings. Description-specific requirements still guide the AI. Existing plans retain their authored roof until revised; changing the control disables stale export and must be applied through a revision or fresh generation.

Roof slabs now accept roofShape (Flat/Gable/Hip), roofAxis (X/Z ridge direction) and roofRise (height above eaves, 0.2?15). Missing fields default to Flat for compatibility. Gable/Hip compile to actual inclined triangular/quad faces over a flat ceiling, with matching exported mesh collision; stacked boxes are not required. Pitched roofs cannot have courtyard holes: compose separate rectangular roofs around open courtyards. All roof geometry stays in the Roof role for Hide Roof. Every roofed part of the main building has a six-unit minimum eaves height; secondary structures have a five-unit minimum. Ceiling and playable floor count stay independent of outer height. The local route checker conservatively treats the pitched roof envelope as solid; Unity uses the actual slopes.

Wall compilation removes occupied wall/roof volume before emitting new wall pieces. Collinear shared boundaries combine their opening cut coordinates and preserve openings even if a duplicate wall omits them. This prevents overlapping rendered wall surfaces/colliders independently of AI instructions, without rewriting saved wall indices or disturbing revision targets. Shared boundaries should still be authored once; contradictory material choices use the first compiled wall, so inspect ambiguous old layouts. Intentional distinct parallel walls keep their spacing.

Upper floor slab thickness/material defines the inter-storey facade band. Exterior walls of the same structure continue a thin band at the same height; roof-height padding never does. When an upper floor stops at the wall centreline, the band is a 0.1-deep recess in the facade. Where another structure (or its wall/roof volume) stands against that facade above the band, `Geometry.FillBandRecess` fills the recess with the wall's material for exactly that stretch, so a garage meets the house without a slot; open sides keep the band. A narrow trim band does not imply another storey. In City colors, sealed roof-height padding continues the nearest exterior wall material from the SAME storey/wing, rather than borrowing an upper-storey colour. The sloped roof stays in its roof material. Orange/grey uses the existing orange wall / grey band / dark-grey roof palette.

Preview/export geometry is shared. Re-export existing plans for wall-join/facade/wing-height improvements; use an AI revision to replace an old stepped roof with a real gable or hip. No importer version change is needed because export version 2 already carries triangle meshes.

### One-storey structures at six-unit height (0.7.2)

Secondary structures use a five-unit minimum since 0.8.1 (below); six still applies to every part of the main building. RoofAssembly.Top applies the minimum to mesh generation, roof supports and validation. A one-storey main building can keep its ceiling at 3.3 with sealed unused volume up to six; it does not need an upper playable floor, upper windows or a contrasting upper-storey facade. Height padding uses the nearest exterior wall's material at the roof's own level, rather than copying an upper storey's colour, as one unstriped block. Orange/grey keeps orange vertical sides and grey roof/ceiling caps.

### Independent floor counts for buildings and wings (0.8.0)

New plans declare structures before geometry: a named ID, rectangular footprint and playable floor count for each independent building or wing. Secondary structures default to one playable storey unless the description asks for more for that part. This applies to workshops, annexes, sheds, storage wings, garages and other additions; the primary building's count is not inherited. Irregular buildings can use adjacent rectangular parts. Structure footprints must not overlap.

Slabs, walls, stairs/ramps and interior details carry structureId. Validation rejects upper elements beyond their owner's floor count, missing declared floors, and main-building upper slabs that extend across a one-storey structure, even if the slab is relabelled. Playable floors must fit their owner's footprint. Invalid layouts are sent through the existing targeted geometry repair; automatic repair preserves the declared structure footprints/counts instead of raising the limits to hide a violation. This validates the AI's declared intent; review the declarations if the AI misunderstood a natural-language request.

A single-storey secondary annex has a 3.3-unit ceiling and solid filler up to five units (0.8.1). It gets no playable upper room or furnishings. Automatic facade bands and extension colours respect the owning structure, so an annex does not inherit a neighbouring building's upstairs appearance. Furnishing rerolls also respect the ownership and floor counts.

Structure metadata saves in the plan and is editable through targeted revisions (the structures collection). Old plans with structures missing/null retain compatibility; a revision about independent floor counts instructs AI to add the declarations and ownership, then repair the affected geometry. New plans must supply the declarations. Unity export remains version 2 triangle geometry. AI interpretation and final character movement still require review.

### Main and secondary structures (0.8.1)

Each structure declaration has a `role`: **Main** for the primary building, including every rectangle an irregular main building is split into, and **Secondary** for garages, sheds, workshops, annexes, pavilions, kiosks and other outbuildings. Main roofs get the six-unit minimum and Secondary roofs a five-unit minimum (`Rules.SecondaryMinimumHeight`, applied by `RoofAssembly.Minimum/Top`); both exist so players cannot parkour out of the map. A one-storey Secondary garage keeps its 3.3 ceiling and gets solid filler to five, so it stays visibly lower than a two-storey house (eaves 6.6). The filler is one solid block in the structure's own wall colour: `Geometry.Box` never cuts roof volumes at storey-band heights. The prompt (`Core/Prompt.cs`) tells the AI to end walls at their own storey and never build the filler itself as tall walls or hollow volume.

Validation (`Core/StructureLayout.cs`) rejects unknown roles and plans that assign roles without at least one Main. `role` is nullable for plans saved before 0.8.1: a null-role structure counts as Secondary when it has fewer floors than the tallest declared structure, otherwise Main, so re-exporting an older house-with-garage plan lowers the garage from six to five units without an AI revision. Legacy plans with no structure declarations keep six-unit padding on every roof. The schema change is generated by `make_schema.py` (plan, revision and furniture schemas).
## Furniture rerolls (0.6.0)

**Furniture and props** has a separate 0?3? density slider, **Reroll furniture**, and **Clear**. Sliders are pending until applied; fresh generation also uses the selected furniture density. Rerolls preserve the camera/floor view and pending point sliders. Clear/0? needs no AI. Simple blockers remain unfurnished.

A furniture reroll replaces only movable props, fixtures, vehicles, debris and outdoor furniture. Walls, floors, roofs, stairs, ramps, materials and landscaping stay unchanged. New detail boxes declare a Furniture, Structure or Landscape category; older plans infer protected trees, planters, window bars, foundations, stair infill and similar parts from names. A protected part protects its whole assembly. Inspect unusual legacy names if classification is ambiguous.

1? uses the plan's original furniture count, counting multipart assemblies as one object; empty plans estimate a baseline from floor area. The baseline saves in the plan and stays fixed across rerolls/clearing, preventing cumulative density growth. Targets cap at 250 assemblies and 900 detail boxes. AI uses the current Normal/Vandalized condition and palette, with furniture-only repair when walking checks fail. Failed/cancelled rerolls retain the previous design. Tight layouts can receive fewer objects than requested.

Furniture changes retain reachable weapon/health/patrol points and remove blocked ones. **Reroll ALL points** replaces all three point groups together using their separate sliders, preserving the furniture. Recommended workflow: settle on furniture, then reroll all points. Per-group reroll/clear buttons remain available.

The profile and generation guidance record the author's tested Ashford south-window reference: **3 units wide ? 1.6 high, sill 1 unit above its floor**. Use this for player jump-through windows, with clear approaches and no bars/glass blocking them. This does not enlarge every window or replace the taller door/NavMesh clearance requirements; final character movement still needs an in-game check.

## Export/import workflow

1. **Save building** writes one `.building` file: a self-contained JSON asset with actual vertex/index/UV arrays, material colors, footprint, category, side requirements, weapon/health/patrol markers, and (since generator 0.9.0) the complete editable document under `source`. **Open building** in the generator reopens it for revisions; there is no separate plan file to keep. Unity's `JsonUtility` ignores `source`.
2. A building that fails the generator's checks saves as a draft: `draft: true`, the plan, and no meshes. The importer refuses drafts ("This is an unfinished draft…"), so they never become prefabs.
3. Drop the `.building` file into the game's Assets folder through Unity's Project window.
4. The ScriptedImporter creates a prefab asset with a root `BuildingDefinition`, combined render meshes, opaque URP Lit materials, and non-convex MeshColliders on Default layer. No Rigidbody is added. Lot asphalt is Y=0 and the root is at the footprint center; interior floors may be raised. North=+Z and East=+X.
5. The inspector offers **Create editable prefab…** to make a prefab variant for manually adding survivor/other spawn markers or adjusting generated ones. This operation uses a preview scene and does not alter the open scene.
6. Add the building to the desired `BuildingSet`. The imported asset inspector offers a set selector and **Add generated building to set**. If using a variant with spawn markers, add that variant's `BuildingDefinition` instead.

The importer validates the export before allocating meshes, rejects unsupported versions/invalid indices/non-finite or out-of-bounds coordinates, and warns when the exported agent dimensions differ from the project. Materials and meshes are sub-assets with stable IDs. Reimporting a changed export updates the model while retaining the root reference.

The export does not include a pre-baked NavMesh. Existing `BuildingPlacementGenerator` calls `NavMeshSurface.BuildNavMesh()` after placement, using the Default-layer physics colliders. Door/window holes stay empty in collision; the importer does not make a convex hull around the whole building. The placement pass now obtains footprint areas from its BuildingSet, largest first, rather than only trying areas 4/2/1. Larger buildings still need a sufficiently large flat plot, matching side requirements, and a nonzero `LargeBuildingPreference` for Complex placement.

Older `.buildingplan` files still open in the generator (saving one produces its `.building`); a `.building` exported before 0.9.0 has no `source` and cannot be reopened, so its `.buildingplan` is still needed to revise it. missing condition/style fields default to Vandalized/City, and old Road/NoRoad names are normalized. Older plans lack entrance-intent markers, so those semantic checks are skipped until the next AI revision. Recompilation/export applies asphalt and roof-height rules. Existing `.building` assets keep their original geometry until saved again from the generator; reimporting in Unity never recompiles the plan. Exports are version 2; importer version 3 accepts legacy version 1 assets and all nine canonical side names plus old aliases, preserving stable sub-asset IDs.

## Geometry scope

Supports rectilinear buildings, multistorey interiors, connected straight stairs/ramps, balcony slabs, actual openings, flat/gable/hip roofs, color materials, box-based details and weapon/health/patrol authoring markers. It does not produce texture images, curved/organic architecture, window glass, moving doors, networked objects or survivor/zombie spawn markers. The AI describes any simplifications in the result summary. Blender is not required.

## Verification and maintenance

The standalone `Tests` project exercises real geometry/validation/export code. The app has an off-screen WPF smoke mode. `Tests/prepare_unity_check.py` creates an isolated Unity project under Temp using installed package paths; `UnityImportSmoke.Run` verifies imported prefabs, physics colliders, URP materials, editable variants, reimport stability, and NavMesh entrance/stair paths without opening or saving game scenes.

Keep the standalone profile current when player/NavMesh settings change. Update both the source JSON and its published copy in `dist`. Export format changes require coordinated app/importer changes and a ScriptedImporter version increment when imported behavior changes. Related documents: `WorldGenerationBuildingPlacement.md`, `PathfindingSystem.md`, and `ZombieAI.md`.
